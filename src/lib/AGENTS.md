## Rules (src/lib)
- Calendar and onboarding readers use mandatory provider allowlists in safe-link-fetch.server.ts at entry and every redirect, plus DNS checks and bounded downloads; arbitrary-domain IP pinning is not claimed because hosted fetch cannot pin arbitrary HTTPS peers.
- Social ingestion (Facebook pages/groups, Reddit, Instagram): one async Apify job per kind per run; an Apify webhook + admin Continue process posts in time-boxed batches, deduped via social_posts, so work survives reloads and timeouts. Stops from the truck's own handle (authorIsTruck vs trucks.facebook/instagram/reddit) auto-approve as source own_post; anyone else's post becomes a pending suggested_stops row the owner approves/edits/rejects — nothing public until approved.
- Every new pending truck (embed, /owner/new, scraper) fires HIGHLEVEL_OWNER_WEBHOOK_URL once via src/lib/owner-webhook.server.ts with a payload built by ownerWebhookPayload (src/data/business.ts, unit-tested) — one place so admin alerts stay consistent and never block saves.
- Claim suggestions are computed server-side (src/lib/claims.functions.ts) with the pure matcher in src/data/claims.ts; only public-safe fields leave the server and pending trucks are only suggested on a confirmed-email match.
- Post → stops: deterministic helpers in src/data/posts.ts (time ranges, several venues per post, post date, venue matching; unit-tested) feed hints to the AI and fill stops it misses; ingestPost in facebook.server.ts is the single path used by the scraper and the Admin paste/screenshot tool.
- Venue addresses resolve via saved venues → confirmed owner stops → Google Places (Maps connector, server-side, Quad Cities bias) and are cached in venues; low-confidence matches become suggested_stops with needs_address_check, even for own posts, so nothing unverified goes public.
- Optional logged-in Facebook scraping reads the FACEBOOK_COOKIES_JSON secret (entered by the admin in Settings) and passes it as the Apify `cookies` input; per-source run results are stored on social_sources (last_status/posts/stops/reason).
- Placeholder truck names (isUnknownTruckName in src/data/posts.ts, unit-tested) never match or create trucks; unnamed posts become a pending truck named after the post author with the original post URL in its description, so admins approve them. Owners' pending trucks also feed social_sources so their own pages are scraped from signup.

- Chat search and MCP share api-search.server.ts and pure agent-*.ts rules for smart locations, food matching and Chicago recurrence; caller-scoped MCP clients preserve OAuth/RLS.
- Google weekly hours snapshots on trucks expand through data/google-hours.ts into marked apify_maps stops shared by public useStops and API/MCP; admin-only refresh batches at most 10 saved Places IDs so public reads never trigger billable lookups.
- Base location confirmation uses confirm_truck_location RPC (admin or active claimed owner), explicit evidence and address-change reset; admin refresh confirms matched fixed addresses, not merchant verification. Google closures archive without deletion, never based on daily closed hours.
- All Apify discovery/social calls use the linked gateway connection so credentials stay server-only. Regional venue matching uses the shared coverage circle; new social-page trucks enter pending review before publication.
- Google Maps city seeds start Apify runs asynchronously and the Admin page polls status/dataset; run-sync calls longer than ~90s fail with gateway 502.
- Enrich priority: pasted post links (read once, never registered as sources), then the truck's own social_sources rows (page/instagram/website/calendar/gmaps) are primary and per-truck — never scan another truck's profile; web research (truck-research.server.ts) and shared group scans run only when own sources find nothing. Per-truck calendar links (kind "calendar") sync in truck-calendar.server.ts via the two-hour job: known confirmed venues become stops, the rest become suggested_stops with needs_address_check.
- Menu summaries: generateMenuSummary in menu.functions.ts writes one AI paragraph to trucks.menu_summary (admin/owner), shown above the menu; never invent dishes or prices.
- Feed conflicts resolve in data/feed-priority after expansion, retaining calendar identities; ingestion protects only direct manual confirmations and saves trusted Facebook corrections instead of treating them as duplicates.
- Social reading: Enrich reads each Facebook/Instagram page or pasted post synchronously (social-direct.server.ts, small Apify job, newest 3 posts, photo/reel links followed) and runs as a queue of one-task requests driven by the progress bar, so no long request can strand a run. Scheduled scans split pages/Instagram into Apify jobs of 8 (meta.runs chunk keys + meta.chunks) because large jobs get "content isn't available"; context.dev results that are only Facebook's login-wall header count as failures. Pure link/item rules live in data/social-read.ts.
- AI calls (image/post/menu readers, Facebook extraction, web research) go through gemini.server.ts when GOOGLE_API_KEY is set, falling back to the built-in gateway when it is not — so removing the key never breaks reading.
